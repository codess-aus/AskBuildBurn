# Review the Diff

The diff is where ownership happens.

Not when Copilot generates the code. Not when the tests pass. When you look at every changed line, understand what it does, and decide: this is what I'm shipping.

That decision — made deliberately, line by line — is what separates a developer who uses AI assistance well from one who's slowly outsourcing their judgment.

---

## The Autopilot Risk

There's a cognitive shortcut our brains take when code looks reasonable: we stop reading it.

This is especially pronounced with Copilot output because:

1. It's syntactically correct (almost always)
2. It follows familiar patterns (by design)
3. It was generated by something that seems confident
4. The tests pass (when they're present)

All of these signals say "this is probably fine." And usually, it is. But "probably fine" is not the standard for production code.

!!! warning "The cost of autopilot review"
    The bugs that slip through autopilot review are not random. They cluster in the places where code looks most like code you've seen before. The familiar shape masks the unfamiliar behaviour.

---

## How to Read a Diff

Reading a diff well is a skill. It's different from reading code. Here's how to approach it:

**Start with the shape:**
What changed? What was added? What was removed? Before reading individual lines, understand the scope of the change.

**Read removals carefully:**
Deletions often carry more information than additions. What was there? Why was it removed? Is it replicated elsewhere or just gone?

**Read additions with scepticism:**
New code is where bugs are. Read every new line as if you wrote it and are about to explain it to someone. Can you?

**Look for unexpected changes:**
Any file touched that you didn't expect? Any function changed that wasn't the target of the refactor? These are signals to investigate.

**Check error handling:**
It's the most commonly omitted part in generated code. Is every error case handled? What happens on null? On network failure? On unexpected input?

---

## The Three Questions for Every Changed File

For every file in a diff, ask:

1. **Why was this file changed?** (If you can't answer, find out before merging)
2. **Is every change here intentional?** (Accidental changes happen more often than you'd think)
3. **Is there anything in this file that I'd want a human to catch before production?** (That human is you, right now)

---

## Using Copilot to Review Copilot

One of the most effective techniques for high-quality reviews is asking Copilot to review its own output.

```
Here is a diff of changes to the authentication module.
Review it as a senior engineer.
Look for:
- Logic errors or edge cases not handled
- Security issues (injection, privilege escalation, data exposure)
- Violations of common patterns visible in the existing code
- Changes that seem unnecessary or risky

Be specific. Cite line numbers.
```

Copilot reviewing Copilot sounds circular — and it can be. The model doesn't have a separate reviewer perspective. But it does have broad pattern recognition, and asking it to critique often surfaces things it didn't consider when generating.

Treat this as a first pass, not a final one. Your eyes still go on the diff.

---

## What Good Review Habits Look Like

- **No rubber-stamping** — "LGTM" on a Copilot-heavy PR with no comment is a risk, not an approval
- **Inline questions** — "Why is this condition flipped here?" is a valid PR comment to yourself
- **Test by reading** — Read the code and mentally trace the execution path before running anything
- **Review small** — Smaller PRs are reviewable PRs. If Copilot generates 800 lines, review 200 at a time

---

## The Review is the Ownership Moment

At the end of a thorough diff review, you should be able to say:

*"I read every line. I understand what each change does. I've considered the edge cases. I'd bet my weekend on this."*

That's the bar. It's not bureaucracy. It's engineering.
